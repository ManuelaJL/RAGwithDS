When the user asks a question, the most relevant documents are loaded. Then I run them to a filter to make sure they actually are relevant (meets_relevance_criteria)
In this filter, I compare the vector representation of the document with that of the query to make sure they are close enough.
I don't have access to the vector representation of the document directly, because it is under the hood. So instead, I create my own cache, with VectorCacheCreator.

Cycle:
1. Embedder uses FileLoader to get the contents of the PDF (currenlty only 1. Will add more later)
It creates an index, i.e. a FAISS vectorstore, which is stored in the file index.faiss
2. VectorCacheCreator creates a cache of each chunk's embedding, saved in vector_cache_for_relevance...jsonl
This is because the chunks' embedding isn't accessible to us. It's blackbox. But we would like to have the
embedding so we can compare how relevant the found results are.
ChunkIds are deterministic, using the filename and page number.
3. (Failed at this step with TinyOllamaChatbot, so instead using: ) GemmaChatbot loads the index/vectorstore
and the vector cache, then chats with the user in an endless loop.
Instead of using qa_chain to get the results directly, we first get the relevant documents via the retriever,
then check via meets_relevance_criteria if each page is close enough to the query (that's where we need the vector_cache).
It merges the relevant pages into a context string, and uses it to call qa_chain_without_retriever.invoke and prints the result.

EMBEDDING_MODEL = "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2"

Summarizer:
Goes through all the documents of a given path, and first makes summaries of each page individually, and then combines them into summaries
of the whole document (and a version that directly summarizes the whole document).
It then saves these summaries in text form, in the summary/output folder, in the same folder structure they were originally in.
